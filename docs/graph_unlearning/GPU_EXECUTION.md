# GPU execution

## Five agents do not mean five model copies

On the RTX 3090: load the 1B checkpoint **once**, create five logical agents with
different ids, prompts and independent seed streams, and point all five at the same
physical handle. Comfortable inside 24 GB.

Describe them honestly as *five logical agents sharing one unlearned model backend* —
never as five independently unlearned agents. `RUN_MANIFEST.json` records
`shared_model_handles` (object identity per profile) and an `agent_note` saying exactly
this. A heterogeneous-agent study with several different checkpoints is future H100 work.

| Agent | Role |
|---|---|
| A | Proposer |
| B | Evidence analyst |
| C | Independent reviewer |
| D | Information integrator |
| E | Finalizer / writer |

Roles and system prompts are identical across all five experimental arms.

## Why the old runner could not do this

`RDLConfig` supported only `agent_a`/`agent_b`; conditions were hardcoded C0–C3C;
`run_episode()` used `agents[0]` and `agents[1]`; delegation stopped after one hop; arms
were hardcoded in `run_leak.py`; generation sat inside nested item/sample loops;
transformers generated one prompt at a time; the store and semantic blocklist were
rebuilt constantly; every result row was flushed and fsynced immediately; scoring and
generation were coupled.

**None of that was changed.** The historical runner is frozen evidence. This is a
separate experiment family with its own runner.

## What the new runner does instead

* **One model handle per unique checkpoint** (`runtime/*_backend.py`,
  `shared_handle_ids()`).
* **Layer-wise batching.** The unit of work is "every node ready at this graph depth,
  across every trajectory in flight" — not one trajectory at a time. `GraphSpec.layers()`
  gives the depths; `plan_layers` assembles the units; `BatchScheduler` chunks them to
  `max_num_seqs`.
* **Continuous batching with per-request seeds** via vLLM on the GPU profiles.
* **A response bank** keyed on backend, backend version, model revision, tokenizer
  revision, the complete serialized prompt including the system message, every decoding
  parameter, and the seed. An entry is reused across arms **only** when all of that is
  byte-identical, so a defence that rewrote the prompt automatically gets a new key. The
  bank records which arms shared each key, which is the audit trail for the reuse.
* **Batched detector calls.** One detector pass per node covering the query, each
  individual input and every combination — not one call per message.
* **Immutable evidence shards.** `shard_size` trajectories accumulate, are written to a
  temporary file, hashed, atomically renamed, and their hash appended to the manifest. A
  killed process leaves a discardable `.tmp`, never a torn committed shard. No fsync per
  row.
* **Generation and scoring are separate phases**, so the generator is unloaded before the
  large NLI evaluator loads.
* **Clean memory snapshots are reused** rather than rebuilt per trajectory.
* **Throughput and peak VRAM are recorded** in `PERFORMANCE.json`.

## Scope limit on vLLM

The graph protocol may use vLLM, whose numbers are only ever compared against other arms
generated by the same backend in the same run. The strict direct Leak@k compatibility
runner stays on `transformers` at batch size 1. vLLM's sampler, kernels and batching do
not reproduce `model.generate` bit for bit, so a result presented as a reproduction of
the released Leak@k generation path must not come from it. A small equivalence audit is
recorded before the graph protocol's vLLM numbers are used.

## Cost model

Per (item, sample) on diamond5 with five arms: 1 (SA) + 4 × 5 = **21** graph
generations, before caching and excluding the readback probe.

| Stage | Items | Samples | Graph generations | Probe generations |
|---|---|---|---|---|
| Smoke | 4 | 2 | **168** | 80 |
| Small discovery | 20 | 8 | 3 360 | 1 600 |
| Main discovery | 50 | 32 | 33 600 | 16 000 |

`rdl graph-plan` prints these before anything is generated, and
`tests/graph/test_scheduler.py` pins the three numbers. Do **not** run the full Cartesian
product of challenges × topologies on the 3090.

## The GPU-readiness gate

Rent the 3090 only when all of these hold:

- [x] every graph, defence, memory, runtime and contract test passes on CPU;
- [x] the 4-item smoke cohort is frozen;
- [x] all five arms resolve;
- [x] DRAGON and GraphForget share one detector object (asserted by test);
- [x] the detector threshold is explicitly marked `diagnostic` or `calibrated`;
- [x] the dry run predicts exactly **168** graph generations;
- [x] resume works after an intentionally interrupted stub run;
- [x] the validation split remains inaccessible (it raises on load);
- [x] one physical model is shared by all five logical agents;
- [x] no scoring API is called during generation;
- [x] `RUN_MANIFEST.json` is written before the first model call;
- [ ] model and tokenizer revisions are pinned in `configs/graph/models/*.yaml`.

The last box is deliberately open: `revision: null` records "unresolved" in the manifest
rather than pretending to a commit. Pin it on the GPU box, where the Hub is reachable.

## Commands

```bash
# on the GPU box, edit ONE line in configs/graph/launch.yaml:
#   active_profile: rtx3090_1b

rdl graph-freeze-cohort --manifest data/cohorts/graph_unlearning_v1/smoke.json --write
rdl graph-plan     --launch configs/graph/launch.yaml
rdl graph-run      --launch configs/graph/launch.yaml --output runs/graph/smoke
rdl graph-score    --run runs/graph/smoke --scorer leakk --device 0
rdl graph-report   --run runs/graph/smoke
rdl graph-finalize --run runs/graph/smoke
```
